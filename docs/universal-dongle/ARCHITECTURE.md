# Universal Hana + Chocofi dongle (EXPERIMENT)

Status: architecture and baseline measurement only. **No switching firmware exists yet.**

## Safety boundaries
- Existing Hana and Chocofi shields, keymaps, pairing records and their standard build workflows remain unchanged.
- All experimental modifications go on `experiment/universal-dongle` in BOTH repositories.
- Never flash the baseline builds as a "universal" firmware; each still supports only its individual board.
- Never erase settings/bonds as a development shortcut. Maintain a separate test dongle or capture a recovery plan before pairing experiments.

## Device and memory boundaries
- Target: Pro Micro footprint nRF52840 clone compatible with ZMK `nice_nano//zmk`, with wired USB and SSD1306 128x64.
- Silicon reference capacity: nRF52840 **1 MiB internal flash, 256 KiB RAM**. This is NOT the available application capacity: MCUboot/UF2, partitioning, settings/NVS, stacks, BLE buffers and LVGL reserve resources.
- Actual board/clone bootloader partition map must be obtained from the produced Zephyr build/linker output; do NOT equate UF2 ZIP or UF2 file byte size with linked flash usage.
- Baseline experiment compiles existing Hana and Chocofi 128x64 USB Studio builds on precisely the same nRF52840 dongle board target.
- Before enabling four peripherals or dual keymaps, capture the linker **Memory region** usage for FLASH and RAM; also save the ELF, MAP, Kconfig and DTS if possible.
- Proposed acceptance guardrails (engineering goals, not measured results): keep at least 15% of application flash and 20% RAM free after linking; confirm BLE stack/resource use under real four-bond/two-connection operation. Fail any build that exceeds linker regions.

## Central design
1. **Stable identity registry** of HANA_LEFT, HANA_RIGHT, CHOCOFI_LEFT, CHOCOFI_RIGHT, bound to persisted BLE identities; never derive board side from connection order.
2. **Connection policy**: initial milestone two live connections to the selected board; store bonds for all four. Maintain a strict active-board gate on all events, status, battery, charge, sensor and disconnection paths.
3. **Position routing**: peripheral and position are distinct namespaces. Do not infer board from matrix position, and do not combine two board transforms or overlapping position indexes.
4. **Keymap isolation**: independent 46-position Hana and 40-position (36 active) Chocofi physical layouts plus combos, hold-taps and Studio-stored runtime settings. Standard ZMK compiles one keymap per device; runtime selection requires an explicit abstraction in keymap/behavior and Studio storage code, not merely 4 BLE connections.
5. **Safe transition**: release held HID usages, discard pending combo/hold-tap work and pressed keys, block old events, disconnect old pair, connect selected pair, reset selected board's layer state, then resume USB HID reports. Switch request must be generated by active board or another reachable control.
6. **UI isolation**: OLED board name, correct side-specific charge/battery, WPM/layer/modifier symbols; Studio should edit only selected board's configuration.
7. **Bond migration**: existing firmware stores peripheral addresses indexed by slot, with `ZMK_SPLIT_BLE_PERIPHERAL_COUNT` compile-time. Plan settings namespace migration and rollback before changing slot count.

## Milestones / gating
A. Compile and record memory footprints of both existing dongles (separate binaries). Establish safe baseline without hardware changes.
B. Compile a USB-only two-board keymap/router skeleton; verify code size and event routing in simulated tests.
C. Add four-identity bond registry and selectable *two-live-peripheral* connection policy.
D. Test switching from active keyboard without repairing, with HID release and correct left/right batteries.
E. Add per-board Studio storage and OLED, test USB/macOS/Windows behavior.
F. Evaluate keeping all four BLE links alive only if memory, radio/power and latency allow it.
